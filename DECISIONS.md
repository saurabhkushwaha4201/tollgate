# 🏛️ Architecture Decisions

This document outlines the core engineering and design decisions made while building Tollgate. Each entry explains the technical context, the options considered, and why the final approach was chosen for a production-grade multi-tenant SaaS backend.

---

## 1. API Key Hashing: SHA-256 over bcrypt

**Context:** We needed a secure way to store API keys in the database.
**Decision:** We chose `SHA-256` instead of `bcrypt`.

**Reasoning:**
`bcrypt` is the gold standard for user passwords because it is computationally expensive by design. That slowness (often ~100ms or more) is the primary defense against offline dictionary and brute-force attacks against low-entropy passwords. 

However, API keys generated by our system are cryptographically secure, fully random 256-bit strings. There is no dictionary to attack. Applying `bcrypt` to an API key adds significant latency to *every single authenticated API request* with absolutely zero added security benefit. `SHA-256` provides instant verification while ensuring the plaintext key is never stored in the database.

---

## 2. Rate Limiting: Sliding Window over Fixed Window

**Context:** Preventing abuse by throttling organization API traffic.
**Decision:** We implemented a **Sliding Window Log** algorithm via Redis instead of a Fixed Window counter.

**Reasoning:**
A fixed window algorithm resets on a hard clock boundary (e.g., at exactly 12:00:00). If an organization has a limit of 60 requests per minute, they could theoretically make 60 requests at 11:59:59 and another 60 requests at 12:00:00. This results in 120 requests hitting the backend within a 2-second span, defeating the purpose of traffic smoothing.

Our sliding window algorithm dynamically counts the number of requests made in the last 60 seconds relative to the *current* timestamp. This strictly enforces the concurrency limit at all times, making burst abuse impossible.

---

## 3. Rate Limiter Concurrency: Lua via EVALSHA over INCR+EXPIRE

**Context:** Ensuring rate limiter counters are accurate under highly concurrent traffic.
**Decision:** We run the rate limit evaluation inside a Lua script executed atomically in Redis via `EVALSHA`.

**Reasoning:**
A naive rate limiter reads the current count (`ZCARD`), checks if it's under the limit, and then writes the new request (`ZADD`). Without atomicity, two concurrent API requests could both read a count of 59, both determine they are allowed to proceed, and both write to the database—pushing the limit to 61.

By embedding this logic in a Lua script, Redis guarantees that the entire script executes as a single, uninterrupted atomic transaction, eliminating Time-of-Check to Time-of-Use (TOCTOU) race conditions. Furthermore, using `EVALSHA` allows us to send a tiny 40-byte SHA-1 hash of the script to Redis rather than the full source code on every call, drastically saving network bandwidth at scale.

## 4. Usage Metering: Dual-Table Architecture

**Context:** Recording API usage for analytics and billing.
**Decision:** We split usage tracking into two tables: `usage_events` (raw data) and `usage_summaries` (aggregated data).

**Reasoning:**
At a moderate scale (e.g., 1,000 requests/minute across 50 orgs), the `usage_events` table accumulates millions of rows per day. If a customer opens their billing dashboard and asks, "How many requests did I make this month?", computing that on the fly would require a full table scan across 30 days of raw events, heavily degrading database performance.

To solve this, we introduced the `usage_summaries` table. A background job pre-aggregates the raw events on an hourly basis. That same billing query now simply sums up ~720 pre-computed rows (30 days * 24 hours), resulting in lightning-fast dashboard queries regardless of the underlying event volume.

---

## 5. Background Aggregation: Idempotent Upserts

**Context:** Designing the cron job that rolls up `usage_events` into `usage_summaries`.
**Decision:** The SQL query uses `ON CONFLICT (org_id, period_start) DO UPDATE` (upsert).

**Reasoning:**
Background workers fail. Servers restart. Network partitions happen. If the aggregator job was a simple `INSERT`, running it twice for the same hour due to a retry would result in duplicate billing data and corrupted analytics. 

By defining a unique constraint on `(org_id, period_start)` and utilizing an upsert, the operation becomes fully idempotent. If the job runs three times for the 10:00 AM window, it simply overwrites the summary with the exact same accurate numbers. This makes deployments, server restarts, and manual backfills completely safe.

## 6. Webhooks Resiliency: Execution Before Insertion

**Context:** Processing asynchronous billing events securely from Stripe.
**Decision:** The webhook handler fully processes the business logic *before* logging the `stripe_event_id` into the database.

**Reasoning:**
We use a `billing_events` table with a `UNIQUE` constraint on `stripe_event_id` as an idempotency key to prevent processing the same webhook twice. 

If we inserted the ID into the database *first*, and then our handler crashed or threw an error midway through processing, the event would be permanently marked as "processed." When Stripe automatically retries sending the webhook a few hours later, our database would reject it as a duplicate, leaving the system in an inconsistent state. 

By executing the business logic first and inserting the idempotency key only upon *success*, a failed handler leaves no trace. Stripe's retry mechanism will then deliver the event again cleanly, allowing the system to self-heal.

---

## 7. Stripe Metadata: Tri-Level Redundancy

**Context:** Mapping Stripe objects back to our internal `org_id`.
**Decision:** We store `org_id` in the Stripe metadata at three levels: Customer, Checkout Session, and Subscription.

**Reasoning:**
Different Stripe webhook events expose different primary objects. For example:
- `checkout.session.completed` provides a Checkout Session object.
- `invoice.payment_failed` provides an Invoice object (which links to a Customer, but not necessarily a Checkout Session).

If we only stored `org_id` on the Checkout Session, processing an invoice failure would require us to make multiple round-trip API calls to Stripe to walk the relationship graph back to the Checkout Session just to find the `org_id`. By aggressively attaching the `org_id` metadata to all three objects during creation, virtually any webhook event we receive can be immediately and synchronously resolved to our internal tenant without external API calls.

---

## 8. Subscription Cancellation: End of Period

**Context:** Handling when a user downgrades their SaaS tier.
**Decision:** We utilize Stripe's `cancel_at_period_end: true` rather than canceling the subscription immediately.

**Reasoning:**
If an organization pays for a Pro tier on June 1st and cancels on June 15th, cutting off their access immediately creates a terrible user experience—they paid for 30 days but only got 15. 

Using `cancel_at_period_end` preserves their Stripe subscription (and thus their Pro access in our system) until the paid cycle naturally concludes. Notably, our database does *not* immediately downgrade them when the cancel button is clicked. Instead, we wait for Stripe to fire the `customer.subscription.deleted` webhook precisely at the end of the billing period. Stripe remains the unquestioned source of truth for time and billing states.
